# Sparkle auto-update integration

This ExecPlan is a living document maintained in accordance with `PLANS.md`
(checked in at the repository root). Keep `Progress` and `Validation and
Acceptance` current as work proceeds.

## Purpose / Big Picture

Laban (a macOS terminal app, SwiftPM package, repo `rrva/laban` on GitHub)
currently ships with a home-grown update checker: the app polls a small JSON
manifest hosted on Google Drive, and when a newer version exists it merely
*opens the zip URL in the user's browser* — the user downloads, unzips, and
replaces the app by hand.

After this change, release builds of Laban update themselves through Sparkle 2,
the standard macOS update framework: the app checks an appcast feed in the
background, downloads the update, verifies its EdDSA signature, and offers to
install and relaunch — no browser, no manual drag-into-/Applications. Release
zips are published as GitHub Release assets on `rrva/laban`, and the appcast
(a small RSS-like XML file Sparkle reads) is committed to the repo root on
`main`, served via raw.githubusercontent.com. Release builds are additionally
signed with the hardened runtime and notarized so Gatekeeper accepts the
downloaded update.

You can see it working by running a packaged release build, pointing its
`SUFeedURL` user default at a test appcast advertising a higher version, and
watching Sparkle's update window appear.

## Context and Orientation

Key terms:

- **Sparkle**: open-source (MIT) macOS update framework. The app embeds
  `Sparkle.framework`; updates are described by an **appcast** (XML feed)
  whose download entries carry an **EdDSA (ed25519) signature**. The private
  half of the key lives in the maintainer's login Keychain; the public half
  ships inside the app (`SUPublicEDKey` Info.plist key).
- **Appcast**: `appcast.xml` at the repository root, committed to `main`.
  Release builds read it from
  `https://raw.githubusercontent.com/rrva/laban/main/appcast.xml` (the
  `SUFeedURL` Info.plist key). Each entry's enclosure points at a zip
  attached to a GitHub Release.
- **Notarization**: Apple scans the signed zip (`xcrun notarytool`) and the
  ticket is stapled to the app. Without it, Gatekeeper blocks downloads on
  other Macs.

Current state (pre-change):

- `scripts/build-app` builds all executables with `swift build` and assembles
  `.build/laban/Laban.app` with five executables flat in `Contents/MacOS/`,
  an Info.plist generated by heredoc (search for `cat > "${bundle_dir}/Info.plist"`),
  and ad-hoc code signing by default. No frameworks are embedded; there are no
  rpaths. Local dev builds stamp version `0.0.0` / build `0`.
- `scripts/package-zip <version>` produces `.artifacts/release/Laban-<version>.zip`,
  signed with `Developer ID Application: Ragnar Rova (3563RJWBQP)`. It stamps
  the Google Drive manifest URL into Info.plist (`LABANUpdateManifestURL`) and
  defaults `CFBundleVersion` to a constant `1`.
- The old checker lives in `Sources/LabanApp/UpdateChecker.swift` (manifest
  fetch + version compare), `UpdateAutoCheck.swift` (polling policy),
  `UpdateAutoChecker.swift` (timers + badge), `UpdateBadgeView.swift` (the
  bottom-left "↓ version" pill), with wiring in `AppDelegate.swift`
  (`checkForUpdates(_:)`), `MainWindowController.swift`, and
  `MenuCommands.swift` ("Check for Updates…" menu item). Tests:
  `Tests/LabanAppTests/UpdateCheckerTests.swift`,
  `Tests/LabanAppTests/UpdateAutoCheckTests.swift`. Doc:
  `docs/release/update-checks.md`.
- Per-worktree isolation: `scripts/resolve-bundle-identifier` gives linked
  worktrees a distinct bundle ID, so their UserDefaults domains are separate.
  Dev builds (version `0.0.0`, no `SUFeedURL`) must never contact the release
  feed — the updater gate enforces this.
- An in-tree reference implementation of the same integration exists in the
  untracked sibling checkout `CodexBar/` (`CodexBar/Scripts/package_app.sh`,
  `CodexBar/Scripts/sign-and-notarize.sh`,
  `CodexBar/Scripts/sparkle_signing_paths.sh`,
  `CodexBar/Sources/CodexBar/CodexbarApp.swift`). Consult it for the framework
  embedding and inside-out signing order; do not copy its release tooling
  verbatim (laban's pipeline stays repo-local, no external `mac-release` tool).
- Sparkle 2.9.3 tools (`generate_keys`, `generate_appcast`, `sign_update`)
  are unpacked at `.artifacts/sparkle/` (gitignored).

## Decision Log

- Decision: Replace the Drive-manifest checker outright instead of running
  both side by side.
  Rationale: user direction; two update mechanisms are more failure modes than
  one. Sparkle subsumes the manual-check menu item and the background poll.
  Date/Author: 2026-08-20 / user-approved plan.
- Decision: Host zips on GitHub Releases, appcast committed to `main`.
  Rationale: Sparkle enclosures need stable direct-download URLs; Drive
  direct-download links are unreliable. `docs/release/update-checks.md` itself
  already recommended GitHub Releases. Same pattern CodexBar uses.
  Date/Author: 2026-08-20 / user-approved plan.
- Decision: `CFBundleVersion` defaults to `date +%s` in `package-zip`.
  Rationale: Sparkle compares `CFBundleVersion`, and the previous constant
  `1` would make every release look identical to the updater. Epoch seconds
  are monotonic and stateless; `LABAN_BUILD_NUMBER` still overrides.
  Date/Author: 2026-08-20 / plan.
- Decision: No Sparkle channels, no custom updater delegate, no
  deferred-install-on-quit.
  Rationale: stock Sparkle behavior covers the requirement; CodexBar's extras
  solve problems laban does not have (menu-bar-only app, beta channel).
  Date/Author: 2026-08-20 / plan.
- Decision: The EdDSA private key lives in a file
  (`.artifacts/sparkle/laban-ed25519-private-key`, mode 600, gitignored via
  `.artifacts/`), not the login Keychain, and `sign_update` /
  `generate_appcast` are invoked with `--ed-key-file`.
  Rationale: `generate_keys` failed with `errSecInteractionNotAllowed`
  (-25308) from the agent's shell — Keychain writes need the user's GUI
  session. The key file is Sparkle's documented new format (base64 of the
  32-byte ed25519 seed, generated with CryptoKit
  `Curve25519.Signing.PrivateKey`), verified by a successful `sign_update
  --ed-key-file` run. The user can later import it into the Keychain with
  `generate_keys -f <file>` and/or stash it in a Passwords-app entry.
  Public key (SUPublicEDKey): `xcKNd45TiWMIJJvqXtH7H4POqTNLwgHjTVrh48lx3u0=`
  Date/Author: 2026-08-20 / implementation discovery.

## Surprises & Discoveries

- Observation: This checkout had no `.external/libghostty-vt` and no zig
  installed, so nothing compiled at first (`'ghostty/vt/terminal.h' file not
  found`). Pre-existing environment gap, unrelated to the Sparkle change.
- Observation: The repo pins zig 0.15.2 (`scripts/fetch-libghostty-vt`,
  enforced by ghostty's `requireZig`), and zig 0.15.2 cannot link *anything*
  against this machine's SDKs: every libc symbol comes back undefined. Root
  cause: macOS 26/27 SDK `.tbd` files list only `arm64e-macos` targets, and
  zig 0.15.2 (targeting plain `arm64-macos`) parses them as empty. zig
  0.16.0 links fine, but ghostty's build.zig uses 0.15-only std APIs.
  Fix used: cloned the 26.5 SDK to `.artifacts/sdk26.5-patched` (via `ditto`)
  and appended `arm64-macos` next to every `arm64e-macos` in its `.tbd`
  files (6098 files, in-place `sed`), then pointed zig's SDK detection at it
  by wrapping the `xcrun` trampoline:
  `.artifacts/FakeXcode.app/Contents/Developer/usr/bin/xcrun` answers
  `-sdk macosx --show-sdk-path/-version` with the patched SDK and forwards
  everything else with `DEVELOPER_DIR` unset; builds run with
  `DEVELOPER_DIR=.artifacts/FakeXcode.app/Contents/Developer` and zig 0.15.2
  on PATH. All of this lives under gitignored `.artifacts/`; no system files
  were modified. zig caches must be cleared (`~/.cache/zig` and the project's
  `.zig-cache`) after switching SDK shims — stale runner objects replay the
  old failure.
  Evidence: `zig cc zigtest.c` → `error: undefined symbol: _printf` against
  the stock SDK; prints `ok` against the patched SDK.
- Observation: A full `swift test` on this machine shows ~250 failures across
  `LabanRendererTests`, `LabanDebugTests`, `LabanCoreTests`, `LabanAppTests`.
  Root cause: this machine's toolchain (Swift 6.4, macOS 27 SDK) compiles
  `.process("*.metal")` resources into `default.metallib`, while
  `MetalRenderer.init` loads `Shaders.metal` *source* from the resource
  bundle (SwiftPM used to copy it verbatim). The lookup misses, init returns
  nil, and every Metal-backed test fails; `ColdLaunchFastBackendTests` and
  `CJKFontSettingsTests` additionally trip over this machine's persisted user
  defaults. Pre-existing toolchain/environment incompatibility, unrelated to
  this change: `Package.resolved` gains only `sparkle`, and
  `LabanRendererTests` links neither `LabanApp` nor Sparkle.
  Evidence: `.build/debug/Laban_LabanRenderer.bundle/Contents/Resources/`
  contains `default.metallib` and no `.metal` sources; the new
  `SparkleUpdatePolicyTests` pass 4/4 in the same run.
- Observation: build-app's first Sparkle rpath change deleted *all* LC_RPATHs
  from the LabanApp binary; the app then failed to launch
  (`Library not loaded: @rpath/libswiftCompatibilitySpan.dylib`). Fix: only
  `/Users/*` rpaths (the SwiftPM build-dir paths the byte scrub would
  corrupt) are deleted; `/usr/lib/swift` and toolchain rpaths stay.
  Evidence: ad-hoc dev bundle now runs `--smoke` → `laban-app: smoke ok`,
  `codesign --verify --deep --strict` passes.
- Observation: Release builds (`swift build -c release`) fail on this machine
  with `unable to open dependencies file (...-primary.d)` because Swift 6.4
  runs release builds through the new SwiftBuild engine and the repo's
  batch-mode release flags (`-no-whole-module-optimization -enable-batch-mode`,
  Package.swift `_fastProfile`) trip it; WMO (`LABAN_WMO_PROFILE=1`) builds
  succeed under the same engine, and `--build-system native` builds succeed
  with batch mode (deprecated-flag warning). Pre-existing toolchain issue,
  unrelated to Sparkle. Verification here uses `LABAN_WMO_PROFILE=1`, which
  Package.swift documents as matching the distributed-release code shape.
  Left unfixed: pinning the deprecated native engine or changing release
  code shape is a repo-infra decision, not part of this change.
- Observation: E2E feed testing taught three things. (1) Sparkle fetches the
  feed with NSURLSession, which does not support `file://` URLs — the check
  silently finds nothing (only `SULastCheckTime` moving betrays that a check
  ran); serving the appcast over `http://127.0.0.1` works (ATS allows
  loopback). (2) The update bundle's `CFBundleIdentifier` must equal the
  running app's, or Sparkle downloads, validates, and then silently aborts
  the install. (3) A terminal app with a live session ignores Sparkle's
  gentle termination; the install completes as soon as the app actually
  quits.
  Evidence: installed test build went from CFBundleVersion 1787297791
  (0.0.0-test) to 1787298791 (0.0.1-test) via the local feed, and the
  updated bundle passes `codesign --verify --deep --strict`.

## Idempotence and Recovery

- `generate_keys` is safe to re-run; it recovers an existing key from the
  Keychain rather than minting a second one.
- `build-app` and `package-zip` rebuild from scratch into `.build/` and
  `.artifacts/`; rerunning them overwrites prior output harmlessly.
  `package-zip` already wipes `.build` unless `LABAN_SKIP_CLEAN_BUILD=1`.
- If the notarization step fails mid-run, the un-notarized zip still exists;
  fix credentials and rerun `package-zip` (or run `notarytool` + `stapler`
  by hand and re-zip with `ditto`).
- Nothing here mutates git state; committing the result is a separate,
  user-approved step.
