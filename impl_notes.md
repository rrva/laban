# Implementation Notes From The Prototype

These notes capture lessons from a working terminal prototype. They are not a
required architecture. The coding agent may choose a different language,
framework, renderer, or project layout as long as `mvp.md` behavior is met and
the choices remain compatible with `spec.md`.

Use this file as a source of known pitfalls and proven behavior, not as a
license to copy prototype constraints into a product implementation.

## What The Prototype Proved

- One terminal session per vertical tab is a good first boundary.
- The tab/sidebar model can live entirely above the terminal core. The terminal
  core does not need to know about tabs.
- Each session should own its pty, child process, terminal state, encoders,
  render state, scrollback, title, and exit status.
- Switching tabs should only switch which session is displayed. It must not
  stop, restart, resize incorrectly, or recreate hidden sessions.
- Terminal title callbacks are enough to keep tab labels and window titles
  useful without inventing a separate title protocol.
- Focus reporting should be sent only when the terminal app requested focus
  events.
- Window resize should update every live session, not only the active one, so a
  background tab is already correct when selected.

## Behavior Worth Preserving

### Session Lifecycle

Session creation should be all-or-nothing. If pty creation, terminal core
creation, encoder creation, render-state creation, or image-state creation
fails, release partial resources and leave the existing tabs untouched.

Session teardown should close the pty, send the normal terminal-disconnect
signal to a live child, reap the child where required, then release terminal
resources. Cleanup should be safe for partially initialized sessions.

If sessions are stored in arrays or moved between containers, any callbacks or
userdata pointing into the session must be rebound after the move. Otherwise a
later title update, pty write callback, or size callback can target stale
storage.

### PTY And Environment

Use a pseudo-terminal, not plain pipes, for interactive shells. Apply initial
rows, columns, and pixel size before the shell begins interactive work. Keep
pty reads from blocking the UI loop, either with non-blocking I/O or a separate
I/O path.

Pick a conservative, widely available `TERM` unless the app installs and
manages its own terminfo entry. Advertise truecolor separately. Do not blindly
inherit automation-oriented color suppression into interactive shells; that can
make rich terminal apps intentionally disable color.

Shell fallback should remain boring: configured shell, then environment shell,
then account shell, then a known-safe system shell.

### Input

Let the terminal core encode terminal keys and mouse events when it provides
encoders. Synchronize encoder options from terminal state before encoding so
application cursor mode, mouse tracking, and extended keyboard protocols are
honored.

Native text input must take precedence over raw modifier interpretation. On
macOS-style keyboard layouts, Option is often how users type real characters.
If the native text system produced text from an Option chord, deliver the text
and mark Option consumed instead of forwarding an Alt-modified chord.

Application shortcuts should run before terminal input. When a shortcut is
handled, drain or consume text generated by that shortcut so it does not arrive
at the shell one frame later.

Unimplemented application-command chords should be swallowed if the command
modifier belongs to the app. Terminal apps should not receive accidental
Super-modified sequences from menu/key-equivalent attempts.

### Rendering

Render from terminal-core render state. Do not parse escape sequences in the UI
layer.

Use terminal-provided color resolution for foreground/background when possible.
Draw explicit backgrounds before glyphs. Handle inverse video by swapping
foreground/background. Draw the cursor only when the terminal says it is
visible and in the viewport.

Clear dirty markers only after drawing the relevant content. If the renderer
has its own damage system, keep terminal-core dirty state and renderer damage
state conceptually separate.

Text rendering needs enough glyph coverage for real TUIs. Box drawing, block
elements, arrows, Braille, geometric symbols, dingbats, currency symbols, and
common private-use symbols matter. If a font atlas is explicit, request these
ranges up front.

### Mouse And Scrollback

Wheel input has two modes. If terminal mouse tracking is active, forward wheel
events to the application. If not, scroll the viewport through scrollback.

A scrollbar or equivalent indicator should be tied to terminal scrollback
state. While dragging it, suppress duplicate mouse delivery to the terminal
app.

### Inline Images

The prototype used the terminal core's image storage and placement metadata.
That part is worth preserving. The prototype's per-frame texture upload is not
production behavior.

A serious renderer should cache uploaded image resources by image identity,
reuse them across frames, and destroy them only after in-flight frames can no
longer reference them.

## Known Pitfalls Found In The Prototype

- A too-specific `TERM` value can break tools on systems where the matching
  terminfo entry is not installed.
- Inheriting `NO_COLOR` from an automation launcher can make interactive TUIs
  render black-and-white even when the terminal supports color.
- Loading a font without explicit symbol ranges can make TUI borders and icons
  degrade to question marks.
- Treating Option as terminal Alt on all macOS layouts breaks characters that
  users type through Option chords.
- Sending unimplemented Command/Super chords to the pty can confuse TUIs.
- Closing a tab while callbacks still point at moved session storage can create
  stale-pointer behavior in C-like implementations.
- Uploading image textures every frame is acceptable for a quick demo, but it
  is a performance and lifetime problem for a production renderer.

## Prototype Choices Not To Treat As Product Requirements

- A single source file is a prototype convenience, not a product architecture.
- A specific GUI toolkit from the prototype should not constrain the new app.
- Temporary image uploads are not a renderer design.
- Fake bold/italic are acceptable placeholders, not a typography goal.
- A fixed tab limit is useful for a prototype, not necessarily for the product.
- Immediate replacement of the final closed tab is an MVP policy, not a
  universal terminal-app rule.

## Candidate Core Boundary

An implementation may expose a terminal core behind a small interface like:

- create session from launch configuration and initial size
- destroy session
- resize session with rows, columns, and cell pixels
- write input bytes to session
- poll or receive pty output
- snapshot or iterate render state
- query title, scrollback, exit state, and dirty state
- encode key events
- encode mouse events
- set effect callbacks

This is a suggested boundary, not a mandated API. The important part is that
window/tab code does not directly own pty lifecycle or terminal parser state.

## Reuse Guidance

Copy behavior before code. If reusing code from the prototype, do it only when:

- the ownership model still matches the new implementation
- the platform/input assumptions still hold
- cleanup paths can be reviewed and tested
- the copied code is smaller and clearer than rebuilding the behavior

Do not preserve prototype code just because it exists. Preserve it when it is
still the simplest correct path to the MVP.

## Suggested Verification Scenarios

Use these when judging whether an implementation preserved the useful behavior:

- open a shell, run commands, and close the tab
- create two tabs, start long-running output in one, switch away and back
- resize the window while multiple tabs exist
- run a fullscreen TUI, then exit it
- type layout-specific characters such as an Option-produced currency symbol
- run colored output and verify color is not suppressed by inherited env
- display box-drawing output and verify it is not rendered as question marks
- scroll shell output with no mouse tracking active
- run a terminal app that enables mouse tracking and verify wheel events go to
  the app
- close a tab whose child is still running
- fail session creation intentionally and verify existing tabs survive
